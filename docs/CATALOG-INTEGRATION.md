# اتصال کاتالوگ به منبع رسمی — نقاط یکپارچه‌سازی

**وضعیت امروز (۲۰۲۶-۱۰-۲۳):** کاتالوگ سایت از **PostgreSQL** خوانده می‌شود؛ ولی دادهٔ داخل آن
«کاتالوگ رسمی تأییدشده» نیست و به‌عنوان **پروتوتایپ** نگه داشته می‌شود. این سند دقیقاً می‌گوید
برای وصل‌کردن منبع رسمی، کدام لایه‌ها باید عوض شوند و چه چیزی نباید دست بخورد.

## ۱) لایه‌بندی فعلی (همان چیزی که باید حفظ شود)

```
UI (src/app · src/components)
        ↓  فقط از این توابع داده می‌گیرد
src/services/catalog.ts      ← مرزِ واحدِ دادهٔ کاتالوگ
        ↓                     getProducts · getProductBySlug · getCategories
        ├─ src/db (Drizzle) → PostgreSQL  (منبع اصلی در runtime)
        └─ src/data/products.ts           (fallback بیلد/قطعی DB — AUTO-GENERATED)
```

قاعدهٔ سخت: هیچ کامپوننتی نباید مستقیم به `db` یا `src/data/products.ts` دست بزند؛
همهٔ مسیرها از `services/catalog.ts` می‌گذرند (`services/catalog.ts` تنها جای `import { db }`).

## ۲) قرارداد داده‌ای که UI انتظار دارد

نوع `Product` در `src/types` مرزِ قرارداد است. برای اتصال API رسمی، پاسخ باید به همین
شکل نگاشت شود (نگاشت را در `services/catalog.ts` بگذارید، نه در کامپوننت‌ها):

| فیلد | الزام | نکته |
| --- | --- | --- |
| `slug` · `name` · `category` | الزامی | `category` باید در جدول `categories` موجود باشد |
| `price` · `weight` | الزامی | قیمت **تومان** و عدد صحیح؛ وزن رشتهٔ فارسی («۵۰۰ گرم») |
| `variants[]` | اختیاری | اگر هست، **قیمت پایه باید دقیقاً با یکی از واریانت‌ها برابر باشد** (قاعدهٔ سنجیده‌شده در `scripts/catalog-audit.py`) |
| `image` · `gallery[]` | الزامی | مسیر محلی `/images/...` یا URL کامل؛ فایل باید وجود داشته باشد |
| `stock` · `stock_status` | الزامی | «موجود» با `stock = 0` ممنوع |
| `features[]` | اختیاری | برچسب «وزن» نگذارید؛ وزن از `weight`/واریانت می‌آید (منبع دوگانه = تناقض) |

## ۳) گام‌های اتصال به API رسمی

1. در `services/catalog.ts` یک پیاده‌سازی تازه (`fetch` به API رسمی) پشت همان امضاها بگذارید:
   `getProducts` / `getProductBySlug` / `getCategories`. **امضاها را عوض نکنید.**
2. نگاشت پاسخ API → `Product` را همان‌جا انجام دهید (تاریخ‌ها با `toDate`، وزن فارسی، قیمت عددی).
3. کش: `fetch(url, { next: { revalidate: 300 } })` یا `unstable_cache` با تگ `catalog`؛
   در صورت نیاز یک مسیر `POST /api/revalidate/catalog` برای پاک‌کردن کش.
4. وقتی API رسمی فعال شد، `src/data/products.ts` (fallback) را **از همان API** بسازید،
   نه از DB قدیمی — وگرنه بیلد بی‌دیتابیس، کاتالوگ کهنه را پیش‌رندر می‌کند.
5. `npm run catalog:export` را فقط پس از تأیید دادهٔ رسمی اجرا کنید.

## ۴) وضعیت‌هایی که UI باید پوشش دهد

| وضعیت | رفتار موجود |
| --- | --- |
| کاتالوگ خالی | `/products` حالت خالی با پیام فارسی نشان می‌دهد |
| DB قطع در runtime | fallback به `src/data/products.ts` + پرچم `wasCatalogDbHealthy()` |
| DB قطع در بیلد | لاگ صریح `[HELSA build]` و پیش‌رندر از fallback |
| slug ناموجود | `notFound()` → ۴۰۴ واقعی (سرور) |
| قیمت نامعلوم | هیچ محصولی با `price ≤ 0` منتشر نمی‌شود (قاعدهٔ `data-integrity.sql`) |
| عکس تأییدنشده | تصویر جای‌نگهدار + یادداشت صریح در PDP |

## ۵) ابزارهای ممیزی که باید در CI بمانند

```bash
python3 scripts/catalog-audit.py        # فقط می‌خواند: شمارش، تکراری، قیمت/وزن، تصویر، متن
python3 scripts/catalog-reconcile.py    # dry-run اصلاحات برگشت‌پذیر (--apply برای اجرا)
bash scripts/deploy-check.sh --full     # دروازهٔ پس از استقرار
```

هر سه باید روی هر تغییر کاتالوگ اجرا شوند؛ `catalog-audit.py` کد خروج ۰ می‌دهد ولی
پرچم‌ها را چاپ می‌کند — پرچم «شمار ≠ مبنا» عمداً خطا نیست، چون شمار کاتالوگ واقعی
تنها با منبع رسمی تأیید می‌شود.
